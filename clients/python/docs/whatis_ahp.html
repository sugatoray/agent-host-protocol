What Is Agent
Host Protocol?

A shared language for apps that want to talk to an AI agent session — keeping every connected client watching the same state, without getting out of sync.

AHP lets many clients watch and control the same AI agent session without getting out of sync. Think of it like Google Docs, but for AI agent sessions.

One session. Many clients. Zero drift.

Google Docs lets multiple people edit the same document simultaneously. Everyone sees the same cursor, the same text, the same state — in real time. AHP does the same for AI agent sessions.

A VS Code window, a web dashboard, a mobile app, and a CLI can all observe — and act on — the exact same agent session. When one client changes something, every other client finds out.

Without AHP, every agent UI would independently invent its own representation for sessions, messages, tool calls, and errors. With AHP, all clients share one contract.

Big Picture

The server owns the real session state. Clients connect to it and ask for things: show me this session, send this message, tell me when something changes. The server replies with state and updates.

+-------------+ AHP messages +----------------+ | VS Code | <------------------------> | | | Web app | | AHP Server | | CLI tool | <------------------------> | | | Mobile app | | Agent Sessions | +-------------+ +----------------+

The Main Idea: One State, Many Views

When a client opens a session it gets a full snapshot. After that, it receives only the small events that describe what changed. If one client renames a session, every other client sees the new title immediately.

Client A AHP Server Client B -------- ---------- -------- opens session ------------> stores session state sends snapshot -------------> sees session renames session -----------> applies action broadcasts update ----------> sees new title

Key Concepts

HOST · SERVER

The Source of Truth

The thing running the agent sessions. The AHP Server owns state and arbitrates all changes — think of it as VS Code's agent host.

AHP Server = the source of truth
CLIENT

Any App That Connects

VS Code UI, a terminal app, a web dashboard, a Python script. This repository ships clients for Rust, TypeScript, Kotlin, Go, Swift, and Python.

SESSION

One Agent Conversation

One AI-agent conversation or workspace interaction. A session holds:

Session |-- chat messages |-- terminal state |-- annotations |-- changesets `-- metadata like title/status
STATE

The Current Shape

Everything you need to render the UI — the full, live picture of a session.

json 
{
  "session": { "title": "Fix login bug", "status": "running" },
  "chat": {
    "messages": [
      { "role": "user",      "text": "Please inspect the auth flow" },
      { "role": "assistant", "text": "I'll look through the login code." }
    ]
  }
}
ACTION

A Small Change Event

Instead of sending the whole state every time, clients and servers exchange small, named actions. An action describes what changed, not what the new state looks like.

json 
{ "type": "session/titleChanged", "title": "Fix login bug" }
Old State + Action = New State
REDUCER

The Rulebook

A pure function that applies an action to state. Every client runs the same reducer — so every client computes the same new state from the same action, independently.

python 
def reduce_session(state, action):
    if action.type == "session/titleChanged":
        state.title = action.title
    return state
SNAPSHOT

Full State at Moment of Join

When a client first connects, it receives a complete snapshot of the session as it exists right now. After that, it only needs the smaller incremental action updates.

On join: "Here is the whole session as it exists right now." Later on: "Message added." "Title changed." "Terminal output appended."

Write-Ahead Reconciliation

Sounds scarier than it is. The client may apply its own action immediately, before the server confirms it — so the UI feels instant, not laggy.

Client Server ------ ------ User renames session Apply change locally UI updates instantly -------> Server receives action Server accepts action <--------- Server echoes action back Client says: "I already applied that one."

When the server echoes the action back, the client recognizes it as already applied and skips re-processing. If the server rejects the action, the client rolls back. Either way, the network round-trip never blocks the UI.

Multi-Client Sync

Two clients watching the same session automatically stay in step. When Client A sends a message, the server updates state and broadcasts the change — Client B sees it without polling.

+-------------+ +-------------+ | Client A | | Client B | | VS Code | | Web UI | +-------------+ +-------------+ \ / \ / v v +----------------+ | AHP Server | | Session State | +----------------+ Client A: "Run tests" ---> Server updates ---> Client B: sees "Run tests"

That is the heart of AHP.

Python Example

Four steps, one async context manager:

python 
from ahp import AhpClient
from ahp.transport import WebSocketTransport

async with AhpClient(
    await WebSocketTransport.connect("ws://localhost:1234")
) as client:
    root_state    = await client.initialize()
    session_state = await client.subscribe("session://example")

    await client.dispatch_action(
        "session://example",
        {
            "type":  "session/titleChanged",
            "title": "Fix login bug",
        },
    )
  1. Connect to an AHP server
  2. Initialize the protocol handshake
  3. Subscribe to one session — receive a snapshot
  4. Dispatch an action that changes the session title

Why AHP Exists

Without a protocol, every agent UI independently invents how to represent the same primitives. Divergence, duplicate bugs, incompatible wire formats.

sessions messages tool calls terminal output file changes errors permissions auth prompts

AHP gives every client and server one shared contract:

message shapes standardized wire format for every message type
state shapes typed, versioned structures clients can rely on
action names canonical event vocabulary (session/titleChanged, …)
error formats consistent error envelopes across all transports
update flow snapshot → incremental actions → reconciliation
versioning protocol negotiation so old clients don't break

A Restaurant Ticket System

The kitchen system is the source of truth. The customer app and the waiter display both read from it. Anyone can update an order, and everyone sees the change — because they share one protocol.

Agent Host Protocol is a standard way for AI-agent clients and servers to share session state, send actions, and keep multiple views of the same agent session synchronized.
