## Detailed Findings

| Severity | Finding | Evidence | Impact | Recommendation |
| --- | --- | --- | --- | --- |
| High | Python requests can hang indefinitely when the host never responds and the transport stays open. | Python `_send_request` stores a future and awaits it directly with no timeout (`src/ahp/client.py:502-516`). TypeScript has `requestTimeoutMs`, timer cleanup, and `RpcTimeoutError` (`../typescript/src/client/client.ts:183-190`, `../typescript/src/client/client.ts:419-425`). | A stalled host can permanently block user awaits and leak pending futures until transport close. | Add optional request timeout configuration to `AhpClient`, reject with a distinct timeout error, and clear pending entries/timers consistently. |
| High | Python has no public event or subscription stream API, so consumers cannot observe several inbound protocol notifications. | Python `subscribe()` returns a state snapshot (`src/ahp/client.py:220-236`) and `_handle_notification()` only handles `"action"` (`src/ahp/client.py:569-571`). TypeScript exposes `events()`, `attachSubscription()`, and per-subscription iterators (`../typescript/src/client/client.ts:198-210`, `../typescript/src/client/client.ts:298-339`) and fans out `root/sessionAdded`, `root/sessionRemoved`, `root/sessionSummaryChanged`, and `auth/required` (`../typescript/src/client/client.ts:630-657`). | Python callers that need session list updates, auth prompts, or raw action streams must poll or patch internals. | Add async iterator or queue-based event APIs, and route all protocol notifications represented in `notifications.py`, not only state actions. |
| High | Python client lifecycle state is implicit and does not prevent use-after-close. | `close()` closes the transport and awaits the reader (`src/ahp/client.py:181-185`), but `_send_request()` and `_send_notification()` do not check a closed client state before sending (`src/ahp/client.py:502-527`). TypeScript tracks `idle/connected/closing/closed`, rejects after shutdown, and closes streams (`../typescript/src/client/client.ts:193-244`, `../typescript/src/client/client.ts:462-507`). | Calls after close depend on transport-specific errors and may leave inconsistent state or pending futures. | Track connection state explicitly, add `connect()`/`shutdown()` or equivalent, reject sends after closure with a client error, and close event/subscription streams when added. |
| High | Python multi-host support is a registry, not a host supervisor. | Python `MultiHostClient` stores already-built clients, delegates initialize/close/get_state/dispatch, and does not own transport creation or reconnect (`src/ahp/hosts.py:36-113`). TypeScript `MultiHostClient.addHost()` resolves durable client ids, creates `HostRuntime`, starts supervision, and exposes host snapshots/events (`../typescript/src/client/hosts/multi.ts:83-164`, `../typescript/src/client/hosts/multi.ts:286-359`). | Python cannot offer parity for multi-host status UX, automatic reconnect, persistent per-host identity, host event fan-in, or stale handle prevention. | Decide whether Python should remain intentionally thin. If parity is expected, introduce `HostConfig`, `ClientIdStore`, `HostRuntime`, host state snapshots, reconnect policy, and aggregate session/agent helpers. |
| Medium | Reconnect replay handling in Python relies on future notifications and does not ingest replay payloads directly. | Python treats non-snapshot reconnect as `ReconnectReplayResult` and leaves state untouched because replayed channels are expected as normal notifications (`src/ahp/client.py:273-289`). TypeScript host runtime gathers replay envelopes from the reconnect result and applies/fans them before publishing connected state (`../typescript/src/client/hosts/runtime.ts:649-719`). | If the protocol result contains replay actions, Python may return from reconnect before state catch-up is applied or may miss replay state if the host expects clients to process result actions directly. | Verify the canonical reconnect result shape and add tests for replay actions in the result. Apply replay envelopes synchronously if the spec requires it. |
| Medium | `dispatch_action()` does local write-ahead but returns no dispatch handle or sequence. | Python allocates `client_seq` internally, applies locally, sends notification, and returns `None` (`src/ahp/client.py:291-318`). TypeScript returns `{ clientSeq }` and lets callers supply a sequence while keeping the counter monotonic (`../typescript/src/client/client.ts:359-379`). | Callers cannot correlate optimistic updates, logs, or acknowledgements with a local dispatch sequence. | Return the assigned `client_seq`, or a small dispatch handle, and consider optional caller-supplied sequence support. |
| Medium | WebSocket transport lacks binary frame handling and close metadata. | Python `RawWebSocketLike.recv()` is typed as `str` and `receive()` returns that string directly (`src/ahp/transport/websocket.py:22-32`, `src/ahp/transport/websocket.py:77-84`). TypeScript accepts text, binary, or parsed frames and records close info (`../typescript/src/client/transport.ts:29-38`, `../typescript/src/ws/transport.ts:119-164`). | Python works for text JSON-RPC WebSocket peers, but gives consumers less diagnostic information and no binary-frame path. | Keep text-only if the Python contract is deliberate; otherwise add bytes handling and expose clean/abnormal close details. |
| Low | Python does not expose a generic server request handler. | Python supports a `ResourceProvider` for resource requests only (`src/ahp/client.py:112-120`, `src/ahp/client.py:484-486`). TypeScript exposes `setServerRequestHandler()` for any server command (`../typescript/src/client/client.ts:213-221`, `../typescript/src/client/client.ts:591-627`). | Future host-initiated commands require changing Python client internals instead of registering handlers externally. | Add a generic handler hook while keeping `ResourceProvider` as a convenience adapter. |
